Исследование пользователей - это единственный по-настоящему хороший способ получения нужной информации

Достаточно изучить отдельных пользователей, чтобы суметь отделить особенности или капризы от общих поведенческих шаблонов.

    В частности необходимо узнать:
  1. Какую цель пользователи ставят при работе с программным обеспечением, для которого вы создаёте дизайн;
  2. Определённыйе задачи, которые они выполняют, чтобы достичь этих целей
  3. Язык и слова, при помощи которых они описывают свои действия;
  4. Их навыки в использовании программного обеспечения, аналогичого тому, над которым вы работаете;
  5. Их отношение к различным вещам с вашим дизайном, влияние разных дизайнов на это отношение.

Анализ рабочих заданий

Анализ рабочих заданий - набор методов, использующих анкетирование или открытое интервью для формирования детального представления о том, как люди в настоящий момент выполняют конкретные задания. В таком исследовании наиболее интересны следующие вопросы:

  • стоящие за заданием реальная цель - для чего пользователь выполняет задания;
  • частота и важность выполнения заданий;
  • триггеры - что служит поводои или сигналом для выполнения задания;
  • зависимости - что требуется для выполнения заданий и что зависит от её выполнения;
  • люди, которые вовлечены в выполнение задания, их роли и зоны ответственности;
  • конкретные действия, которые требуется выполнить;
  • решения, которые необходимо принять;
  • информация, которая нужна для принятия решений;
  • ошибки и исключительные ситуации - что может пойти не так;
  • способы исправить ошибок и обработок исключений.

Метод фокус - групп.

Метод фокусных групп заключается в опросе специально отобранной группы пользователей. В исследование, которое обычно продолжается около 2 часов, вовлекается от 6 до 9 пользователей.

Ответы на вопросы

  1. Технология разработки ПО - это упорядоченная система методов, правил, этапов и инструментов для создания качественных и надёжных компьютерных программ.
  2. Технология состоит из:
    • Методология: принципы, концепции и методы разработки.
    • Инструменты: среды разработки, компиляторы и CASE-средства.
    • Организация: стандарты, распределение ролей и процессы управления.
  3. Жизненный цикл - охватывает весь период от идеи до вывода ПО из эксплаутации.
  7. Основыне стандарты:
    • Сопровождение необходимо, потому что после внедрения ПО требуется:
      • исправлять обнаруженные ошибки;
      • устранять проблемы безопасности;
      • адаптировать программу к новым ОС, оборудованию и требованиям;
      • добавлять и изменять функционаольность;
      • повышать производительность и надежность.

Модели жизненного цикла: каскадная, инкрементная, спиральная, интеративная.

  • Задачи
  • Образовательные:
    • Раскрыть понятие"модель жизненного цикла ПО".
    • Изучить четыре основные модели: каскадную, инкрементную, спиральную, итеративную.
    • Рассмотреть схемы, преимущества и недостатки каждой модели.
    • Научиться сравнивать модели по ключевым критериям.
  • Развивающие:
    • Развивать аналитическое мышление при выборе модели для проекта.
    • Формировать умение работать с технической документацией.
    • Развивать навыки системного подхода к разработки ПО.
  • Воспитательные:
    • Формировать профессиональную культуру разаработчика.
    • Воспитывать ответственность за выбоор технологических решений.
    • Развивать умение работать в команде.

    Четыре основные модели:

    Модель Суть Ключевая особенность
    Каскадная Этапы строго последовательно Возврат назад невозможен
    Инкрементная Проект разбит на части Каждая часть - полный цикл
    Спиральная Витки спирали Акцент на анализ рисков

    Жизненный цикл ПО

  • Это период времени от момента появления идеи о создании программного продукта до момента его полного вывода из эксплауатации.
  • Основные этапы жизненного цикла:
    • Анализ требований
    • Проектирование
    • Разработка(кодирование)
    • Тестирование
    • Внедрение
    • Сопровождение
  • Модель жизненного цикла - это схема которая описывает, как именно эти этапы связаны между собой: последовательно, параллельно, циклически и т.д.

    • Каскадная модель

  • Год появления: 1970, Уинстон Ройс
  • Этапы вополняются строго последовательсно.
    Переход к следующему этапу возможен только
    после полного завершения предыдущего.
    Возврат назад не прудусмотрен.

    • Плюсы каскадной модели:

    • Акцент на анализ рынков - снижает вероятность провала
    • Прототипирование - зказчик видит резултат рано
    • Хорошо рабоатет длясложных и рискованных проектов
    • Можно менять требования на каждом витке

    Минусы каскадной модели:

    • Сложная в управлении
    • Требует оптыной командны
    • Дорогостоящая (много прототипов)
    • Не подходит для маленьких проектов

    Когда применять каскадные модели:

    • Крупные, сложные, рискованые проекты
    • Проекты с
      • неопределёнными требованиями
    • Когда важна безопасность и надёжность (например, медицина, авиация)

    3.Инкрементая модель(Incremental)

  • Год появления:1980-е.
  • Суть
  • Проект разбивается наинкременты(части). Каждый инкремент — этополный цикл разработки(от требований до внедрения), но для части функциональности. Продукт растёт постепенно.
  • Схема
  • text
  • Инкремент 1: Требования → Проект → Разработка → Тест → Внедрение (ядро системы) Инкремент 2: Требования → Проект → Разработка → Тест → Внедрение (доп. функции) Инкремент 3: Требования → Проект → Разработка → Тест → Внедрение (ещё функции) ...
    • Плюсы
    • Заказчик видит результатпосле каждого инкремента
    • Можноизменять требованиямежду инкрементами
    • Раннее тестирование и отладка
    • Можноначать использоватьпродукт раньше
    Минусы
    • Требуетхорошего планированияархитектуры
    • Нужно чётко определитьграницыкаждого инкремента
    • Возможны проблемыинтеграциимежду частями
    Когда применять
    • Крупные проекты можно разбить на части
    • Когда заказчик хочет видеть прогресс
    • Проекты с эволюционирующимитребованиями

    Спиральная модель

  • Год появления: 1986, Барри Боэм
  • Это эволюция инкрементной модели, где каждый виток спирали - это полный цикл разработки с акцентом на анализ рисков. Каждый виток проходит 4 фазы:
    • Определение целей - что делаем на этом витке?
    • Анализ рисков - что может пойти не так?
    • Раззработка и тестирование - создание прототипа.
    • Планирование следующего витка - что делаем дальше?

    Плюсы спиральной модели:

    • Акцент на анализ рынков - снижает вероятность провала
    • Прототипирование - зказчик видит резултат рано
    • Хорошо рабоатет длясложных и рискованных проектов
    • Можно менять требования на каждом витке

    Минусы спиральной модели:

    • Сложная в управлении
    • Требует оптыной командны
    • Дорогостоящая (много прототипов)
    • Не подходит для маленьких проектов

    Когда применять спиральные модели:

    • Крупные, сложные, рискованые проекты
    • Проекты с
      • неопределёнными требованиями
    • Когда важна безопасность и надёжность (например, медицина, авиация)

    Итеративная модель

  • Год появления: как самостоятельная модель — 1990-е
  • Проект разбивается на итерации (повторения).
    Каждая итерация — это полный цикл разработки,
    но результат каждой итерации — это улучшенная версия одного и того же продукта.
    В отличие от инкрементной модели, где добавляются новые функции,
    в итеративной — улучшается уже существующее.

    • Плюсы итеративной модели:

    • Гибкость — можно менять требования
    • Раннее тестирование и обратная связь
    • Постепенное улучшение качества
    • Снижение рисков — ошибки видны рано

    Минусы итеративной модели:

    • Требует вовлечённости заказчика на каждой итерации
    • Сложнее планировать общий бюджет и сроки
    • Может «расползтись» по времени — нет чёткого конца
    • Требует опытной команды

    Когда применять итеративную модель:

    • Проекты с нечёткими или меняющимися требованиями
    • Крупные проекты, которые нужно постоянно улучшать
    • Веб-приложения, мобильные приложения

    Требования к ПО

    1. Что такое требование к ПО?

      Требование к программному обеспечению — это описание того, что программа должна делать, какими свойствами обладать и какие ограничения соблюдать.

    2. Чем функциональные требования отличаются от нефункциональных?

      Функциональные требования описывают, что должна делать система: какие функции выполнять и какие действия поддерживать.

      Нефункциональные требования описывают, как должна работать система: производительность, безопасность, надёжность, удобство использования и другие характеристики.

    3. Какие уровни требований вы знаете?
      • Бизнес-требования — цели и задачи организации или проекта;
      • Пользовательские требования — потребности и задачи пользователей;
      • Системные требования — подробное описание функций и характеристик программной системы.
    4. Что описывают бизнес-требования?

      Бизнес-требования описывают цели создания системы, потребности организации, ожидаемый результат и задачи, которые программа должна помочь решить.

    5. Что такое User Story?

      User Story — это краткое описание требования с точки зрения пользователя. Обычно используется форма: «Как [роль], я хочу [действие], чтобы [цель]».

    6. Какие стандарты регламентируют работу с требованиями?
      • ISO/IEC/IEEE 29148 — устанавливает процессы и требования к инженерии требований;
      • IEEE 830 — известный стандарт, описывавший требования к SRS;
      • ISO/IEC 25010 — описывает модель качества программного продукта.
    7. Что фиксируется в SRS?

      SRS (Software Requirements Specification) — спецификация требований к программному обеспечению. В ней фиксируются:

      • назначение и область применения системы;
      • функциональные требования;
      • нефункциональные требования;
      • ограничения и зависимости;
      • требования к интерфейсам и взаимодействию системы;
      • условия и критерии приёмки.
    8. Чем Agile-подход к требованиям отличается от классического?

      В классическом подходе требования стараются подробно определить и зафиксировать заранее, до основной разработки.

      В Agile требования формируются и уточняются постепенно, небольшими частями, с постоянной обратной связью от заказчика и пользователей. Изменения требований допускаются даже в процессе разработки.

      Современные принципы и методы разработки программных приложений

      1. Программная инженерия

      Программная инженерия (Software Engineering) — это область науки и практики, которая занимается разработкой, внедрением и сопровождением программного обеспечения с применением инженерных подходов.

      Цель программной инженерии:

      • создание работающего программного обеспечения;
      • обеспечение надёжности;
      • обеспечение возможности сопровождения и изменения ПО;
      • соблюдение сроков и бюджета;
      • обеспечение качества программного продукта.

      Программирование — часть программной инженерии, но не вся она.

      2. Отличие программирования от программной инженерии

      Программирование Программная инженерия
      Написание программного кода Весь жизненный цикл ПО
      Может выполнять один разработчик Обычно работает команда
      Главная цель — чтобы программа работала Цель — чтобы ПО работало надёжно и долго
      Основное внимание — коду и синтаксису Процессы, качество и управление
      Личный результат Продукт для пользователей

      3. Основные области программной инженерии

      1. Управление требованиями — определение того, что должно делать ПО.
      2. Проектирование — разработка архитектуры и структуры системы.
      3. Разработка — написание программного кода.
      4. Тестирование — проверка правильности работы ПО.
      5. Сопровождение — исправление ошибок и развитие системы.
      6. Управление проектом — организация разработки, сроков и ресурсов.
      7. Управление качеством — контроль качества ПО.
      8. Управление конфигурациями — контроль версий и изменений проекта.

      4. Современные принципы разработки ПО

      Модульность — система разделяется на независимые модули.

      Абстракция — скрытие деталей реализации и выделение главного.

      Инкапсуляция — объединение данных и методов работы с ними.

      Иерархия — организация системы по уровням и слоям.

      Повторное использование (Reuse) — использование существующего кода и компонентов.

      Слабая связанность (Loose Coupling) — минимальная зависимость компонентов друг от друга.

      Высокая связность (High Cohesion) — каждый модуль выполняет логически связанные задачи.

      Расширяемость (Extensibility) — возможность добавлять новую функциональность.

      Тестируемость (Testability) — возможность удобно проверять систему и её компоненты.

      5. Принципы SOLID

      S — Single Responsibility Principle — принцип единственной ответственности. Один класс должен иметь одну основную задачу.

      O — Open/Closed Principle — принцип открытости/закрытости. Код должен быть открыт для расширения, но закрыт для изменения.

      L — Liskov Substitution Principle — принцип подстановки Барбары Лисков. Объект дочернего класса должен заменять объект родительского класса без ошибок.

      I — Interface Segregation Principle — принцип разделения интерфейсов. Лучше использовать несколько небольших интерфейсов, чем один большой.

      D — Dependency Inversion Principle — принцип инверсии зависимостей. Зависеть следует от абстракций, а не от конкретных реализаций.

      6. Другие принципы разработки

      DRY — Don't Repeat Yourself — не повторяй себя. Не следует дублировать один и тот же код.

      KISS — Keep It Simple, Stupid — система и код должны оставаться максимально простыми.

      YAGNI — You Aren't Gonna Need It — не следует реализовывать функциональность, которая пока не нужна.

      Boy Scout Rule — после работы с кодом следует оставлять его немного чище, чем он был.

      Fail Fast — ошибка должна обнаруживаться как можно раньше.

      Separation of Concerns — разные задачи и ответственности должны быть разделены между компонентами системы.

      7. Классические методы разработки

      Waterfall (каскадная модель) — последовательное выполнение этапов разработки.

      V-модель — развитие каскадной модели, в которой тестирование связано с каждым уровнем разработки.

      Incremental (инкрементная модель) — продукт создаётся отдельными частями — инкрементами.

      Iterative (итеративная модель) — продукт постепенно улучшается в результате повторяющихся циклов.

      Spiral (спиральная модель) — разработка выполняется циклами с обязательным анализом рисков.

      8. Гибкие методы разработки (Agile)

      Agile — гибкий подход к разработке ПО, позволяющий адаптироваться к изменениям требований.

      Scrum — работа выполняется спринтами, используются роли и артефакты, регулярно проводится оценка результата.

      Kanban — визуализация рабочего процесса и управление потоком задач с использованием ограничения незавершённой работы (WIP).

      XP (Extreme Programming) — парное программирование, TDD и частая интеграция.

      Lean — устранение потерь и оптимизация процесса разработки.

      FDD (Feature-Driven Development) — разработка ориентирована на функциональные возможности продукта.

      DSDM (Dynamic Systems Development Method) — гибкая методология разработки динамических систем.

      9. DevOps и CI/CD

      DevOps — подход, объединяющий разработку и эксплуатацию ПО.

      CI — Continuous Integration — непрерывная интеграция изменений в общий код проекта.

      CD — Continuous Delivery — непрерывная поставка подготовленных изменений.

      CD — Continuous Deployment — непрерывное автоматическое развёртывание изменений.

      10. Методы тестирования

      TDD (Test-Driven Development) — сначала создаётся тест, затем код.

      BDD (Behavior-Driven Development) — разработка ориентирована на поведение системы.

      ATDD (Acceptance Test-Driven Development) — разработка через приёмочные тесты.

      Unit testing — тестирование отдельных функций или компонентов.

      Integration testing — проверка взаимодействия модулей.

      System testing — проверка всей системы.

      Regression testing — проверка того, что новые изменения не сломали существующую функциональность.

      11. Роли в команде разработчиков

      Product Owner — отвечает за продукт и приоритеты.

      Scrum Master — помогает команде и устраняет препятствия.

      Team Lead — технический руководитель команды.

      Architect — отвечает за архитектуру системы.

      Analyst — работает с требованиями.

      Developer — разрабатывает программный код.

      QA — отвечает за качество и тестирование.

      DevOps — занимается автоматизацией и развёртыванием.

      Designer — разработка пользовательского интерфейса.

      12. Методологии командной работы

      Scrum — спринты продолжительностью 2–4 недели, ежедневные встречи, планирование, обзор результатов и ретроспектива.

      Kanban — визуальная доска, управление потоком задач и ограничение WIP.

      XP — парное программирование, TDD и частая интеграция.

      Waterfall — последовательные этапы и формальные роли.

      13. Практики командной работы

      Daily Standup — короткая ежедневная встреча примерно на 15 минут.

      На Daily Standup обсуждается:

      • что сделано;
      • что будет сделано;
      • какие есть препятствия.

      Code Review — проверка кода другими разработчиками.

      Pair Programming — два разработчика работают над одним кодом.

      Retrospective — анализ прошедшего спринта и процесса работы.

      Planning Poker — коллективная оценка сложности задач.

      Sprint Review — демонстрация результата заказчику.

      Backlog Refinement — уточнение и подготовка задач из Backlog.

      15. Scrum-процесс

      Product Backlog → Sprint Planning → Sprint Backlog → Sprint → Sprint Review → Increment → Retrospective → следующий Sprint

      Во время спринта команда выполняет задачи и проводит Daily Standup.

      16. Современные тенденции разработки ПО

      • Микросервисы — система состоит из небольших независимых сервисов.
      • Контейнеризация — например, Docker и Kubernetes.
      • Облачные технологии — AWS, Azure, Google Cloud.
      • Serverless — выполнение кода без самостоятельного управления серверами.
      • Low-code / No-code — создание приложений с минимальным количеством программирования.
      • AI-assisted development — использование ИИ при разработке.
      • DevSecOps — интеграция безопасности в процессы разработки и эксплуатации.
      • Platform Engineering — создание внутренних платформ для разработчиков.

      Вопросы для самоконтроля

      1. Что такое программная инженерия?

      Программная инженерия — область науки и практики, которая занимается разработкой, внедрением и сопровождением программного обеспечения с применением инженерных подходов.

      2. Чем отличается программирование от программной инженерии?

      Программирование в основном связано с написанием программного кода, а программная инженерия охватывает весь жизненный цикл ПО: требования, проектирование, разработку, тестирование, сопровождение, управление качеством и проектом.

      3. Перечислите принципы SOLID.

      1. S — Single Responsibility — единственная ответственность.
      2. O — Open/Closed — открытость для расширения, закрытость для изменения.
      3. L — Liskov Substitution — подстановка Барбары Лисков.
      4. I — Interface Segregation — разделение интерфейсов.
      5. D — Dependency Inversion — инверсия зависимостей.

      4. Что означает DRY, KISS, YAGNI?

      DRY — Don't Repeat Yourself — не повторяй себя.

      KISS — Keep It Simple, Stupid — сохраняй простоту.

      YAGNI — You Aren't Gonna Need It — не реализуй то, что пока не нужно.

      5. Какие гибкие методологии вы знаете?

      Scrum, Kanban, XP, Lean, FDD, DSDM.

      6. Что такое Scrum? Какие роли в нём есть?

      Scrum — гибкая методология разработки, основанная на работе короткими спринтами.

      Основные роли:

      • Product Owner — отвечает за продукт и приоритеты;
      • Scrum Master — помогает команде и устраняет препятствия;
      • Team — выполняет разработку продукта.

      7. Что такое Code Review и зачем он нужен?

      Code Review — проверка программного кода другими разработчиками.

      Он используется для контроля качества кода и выявления ошибок.

      8. Что такое CI/CD?

      CI/CD — набор практик автоматизации интеграции, поставки и развёртывания программного обеспечения.

      CI — Continuous Integration — непрерывная интеграция.

      Continuous Delivery — непрерывная поставка.

      Continuous Deployment — непрерывное развёртывание.

      9. Какие инструменты командной работы вы знаете?

      • Git, GitHub, GitLab — управление версиями;
      • Jira, Trello, Asana — управление задачами;
      • Slack, Teams, Discord — коммуникация;
      • Confluence, Notion — документация;
      • Jenkins, GitHub Actions — CI/CD;
      • Figma — дизайн;
      • Miro — совместная работа.

      10. Какие современные тенденции в разработке ПО вы знаете?

      Микросервисная архитектура, контейнеризация, облачные технологии, Serverless, Low-code/No-code, использование ИИ при разработке, DevSecOps и Platform Engineering.
